# WatchAlong v1.0.1 — Drift Correction Fix

## Priority 1 — Fix inverted timeline/playback rate (root cause of drift oscillation)

Read: `src/renderer/src/App.tsx` lines 220-230, 590-600, 1395-1420; `src/renderer/src/sync/SyncController.ts` lines 545-565, 577-588; `src/renderer/src/sync/timeline.ts` lines 54-60.

**The bug:** `sessionRef.current.movieRateCorrection` is 1.001 (movie should be ahead and play 0.1% faster). But `movieTimelineCorrectionFromPlaybackMultiplier` inverts it at **four call sites**, so the timeline expects the movie to be *behind* while playback drives it *faster*. They fight, causing perpetual oscillation.

**The four sites that need fixing:**

1. `App.tsx:226` — `getMovieRateCorrection` callback passed to SyncController
2. `App.tsx:598` — builds `movieStartsAtReaction` / effective offset shown in the UI
3. `App.tsx:1404` — `setMovieRateCorrection` when computing current movie time
4. `App.tsx:1409` — `setMovieRateCorrection` when recalculating stored offset

All four must use `sessionRef.current.movieRateCorrection` directly, not `movieTimelineCorrectionFromPlaybackMultiplier(...)`.

**Preferred approach:** Remove `movieTimelineCorrectionFromPlaybackMultiplier` entirely and store a single value — `movieRateCorrection` (1.001 = "movie runs 0.1% fast") — used as both the timeline mapping multiplier and the playback multiplier. This collapses the dual-convention into one source of truth and makes inversion impossible.

**Also fix:** In `SyncController.ts`, collapse the two controller callbacks (`getMovieRateCorrection` + `getMoviePlaybackMultiplier`) into a single `getMovieRate()`. The default for `moviePlaybackMultiplier` (line 551-557) should use `this.movieRateCorrection()`, not its inverse.

**Also fix:** `correctedRate()` dead zone (SyncController.ts lines 577-588). The <0.03s and <0.10s branches both return `basePlaybackRate` with no correction. Change the 0.03-0.10s branch to `basePlaybackRate * (1 - driftSeconds * 0.3)` — this is continuous with the 3% hard-soft boundary at 0.10s.

**Tests that will need updating:**
- `SyncController.test.ts:172` — "defaults playback multiplier to the inverse timeline correction" — asserts the bug
- `SyncController.test.ts:163-169` — asserts inverted rate in playback multiplier test
- `SyncController.test.ts:180-188` — asserts movieTime=99.9 when it should be 100.1
- `App.test.tsx:500` — "preserve sync point when changing rate" — offset expectation changes

**Contract:**
- With movieRateCorrection=1.001: movieTime = reactionTime * 1.001 + offset (ahead, not behind)
- With movieRateCorrection=1.001: reaction plays at 1×, movie plays at 1.001×
- Changing rate presets must not cause a position jump (the "preserve sync point" behavior)
- Drift must not oscillate during 10-minute playback at 1.001× correction
- `npm run typecheck` and `npm test` must pass

## Priority 4 — Fix subtitle parser trailing whitespace bug

Read: `src/renderer/src/subtitles.ts`.

**The bug:** The parser splits blocks with `.split(/\n{2,}/)`. Blank lines with trailing spaces (e.g., `\n \n`) don't match this regex, causing adjacent subtitle blocks to merge and cues to drop silently.

**Fix:** Change the block split to handle whitespace-only lines: `normalized.split(/\n\s*\n/)`.

**Also:** When `parseSubtitleText` returns an empty array for a non-empty file, show an error: "This subtitle format isn't supported. Use SRT or VTT."

**Edge case guard:** A valid VTT file containing only a `WEBVTT` header with no cues would parse to zero cues and trigger a false error. Check that the file has content beyond the header before showing the error.

**Contract:** Subtitle files with blank lines containing trailing spaces must parse correctly. Non-empty files with no parseable cues must show an error. Valid WEBVTT-header-only files must not trigger a false error. `npm test` must pass (add test cases for trailing whitespace and WEBVTT-only).
