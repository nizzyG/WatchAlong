## Agreed v1.1 QoL scope (in order)

### 1. Session resume position (bug fix)

The sync is saved when you close a session, and the UI shows where you were in the reaction. But when you reopen a previously closed session, playback starts from the beginning. The offset saves but the playback position (`lastReactionTimeSeconds`) does not restore. The position is persisted; the player just isn't reading it on open. Likely a small fix. Verify manually before calling it done.

### 2. Entry-experience overhaul: download progress + autosync roll-in

Two coupled improvements to the "I have a link" to "I'm watching" flow.

**Download progress (bug/UX):** The Patreon progress bar currently vanishes mid-download because patreon-dl emits log lines, not parseable percentages — so `event.percent` is null and the bar stops rendering. The YouTube bar works but shows only a bare percentage with no speed or ETA. Fix both:
- **Patreon:** Replace the vanished bar with an honest indeterminate progress indicator (animated, phase-based) showing the current stage ("Fetching post," "Downloading media," "Finalizing"). patreon-dl doesn't give us real percentages; don't fake one. Communicate "working, here's the stage" without lying about precision.
- **YouTube:** yt-dlp's `--progress-template` can surface speed, ETA, and fragment counts. Show "47% — 4.2 MB/s — 2 min left" instead of a bare number. The data is there; surface it.

**Autosync roll-in (UX):** Remove the "download complete, press sync" interstitial. After the reaction download completes, roll straight into autosync so the ~30s detection feels like the tail of the download weight, not a separate gate. The user experiences one continuous "getting your reaction ready" motion instead of download → click → wait → play.

### 3. Name pairings from movie + reactor

Auto-generate session titles from reaction metadata (movie title + reactor channel) instead of defaulting to the filename. Most of the metadata is already downloaded (patreon-dl carries channel name, post title; yt-dlp can emit similar). The session title currently defaults to the filename, which reads like a stub. "V for Vendetta — LiteWeight Gaming" is the target shape. Low effort, high perceived polish.

### 4. Three library views + reactor profile pictures (headline feature)

The headline QoL feature of v1.1. Once the library grows past ~10 pairings, the flat grid stops serving discovery.

- **a. Movie-Reactor pairings** (current view, preserved)
- **b. By Reactor** (new) — shows all pairings available from each reactor
- **c. By Movie** (new) — shows all reactor pairings available for each movie

**Reactor profile pictures:** The patreon-dl metadata already includes `avatar.jpg`. yt-dlp can grab channel thumbnails with the right flags. Faces make the "by reactor" view genuinely better — humans navigate by faces. Bundle this with the library views; it only makes sense because of them.

**Scope note:** Pure renderer work. No new IPC, no new backend, no new session-model fields. The session already has `reactionPath` and `moviePath` with enough identity to group on. Medium effort, contained.

### 5. Full rewrite of public-facing documentation (parallel track)

Coordinator work, runs in parallel with everything else. Double down on legality by doubling down on media ownership over streaming licenses, and on supporting content creators by paying for Patreon subscriptions. Positive language. Built for Speechify. Saint-Exupéry (nothing left to take away). Carlin (no euphemism, plain words). Applies to: README, FAQ, landing-page copy, in-app copy where it touches the user.

## Deferred to v1.2+

- **Letterboxd integration** — no public API; would require scraping, which is fragile and pulls the project toward third-party network calls it currently avoids. Build on the library views first; evaluate demand later.
- **Companion mobile app** — separate product with separate versioning. Not a port: streaming to a phone means a local HTTP server, a sync-state protocol, a separate client (React Native or native), and a new testing surface. Shares the sync engine; not a feature you bolt on.
- **Background autosync (start playback during detection)** — rejected for v1.1. The autosync roll-in (#2) solves the perceived-latency problem better: make detection feel like the tail of the download rather than interrupting playback. See Creative Director's reframe, 2026-07-13.
